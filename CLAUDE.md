# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

The MySQL Galera LogicModule suite: 3 modules (2 DataSources, 1 PropertySource) and a dashboard
for Galera clusters (MariaDB Galera Cluster, Percona XtraDB Cluster, Galera Cluster for MySQL),
built 2026-11-23 from the note in `docs/original-design.rtf`. `docs/design.md` is the design: what
was kept and changed from that note, the module set, and **the one verification record** (its
section 4). Public repo; the workspace `..\CLAUDE.md` scrub rule applies.

## Layout

- `modules/*.json` -- compact definitions; `build/build.py` expands them to LogicMonitor's export
  shape. `"autoDelete"` (never `autoDeleteInstances`, which the import reads inverted),
  `"conditional"` (may legitimately not print; the harness checks every other datapoint prints
  on a Galera 3 fixture) and `"statusNames"` are build keys.
- `scripts/*.groovy` -- bodies; the build prepends the closures each reaches from
  `scripts/lib/galera_common.groovy`, without comments. `MySQL_Galera.ad.groovy` is the discovery
  of both DataSources.
- `dashboards/MySQL_Galera_Cluster.json` -- generated by `build/make_dashboard.py` with the
  skill's `lm_dashboards.Dashboard`; committed, and checked by every build. Once it has been
  imported and adjusted in a portal, replace it with the portal's export and stop regenerating it.
- `tests/` -- `GaleraTestSupport.groovy` (runs a built script as a Collector would, each
  script compiled once; shared by both test programs, on the classpath via `-cp tests`),
  `harness.groovy` (fixtures in `tests/fixtures/`, through the `galeraTestFetch`
  binding seam), `live.groovy` + `live.sh` (a real MariaDB Galera cluster in Docker, no seam),
  `galera/` (the node image), `docker-compose.yml`.
- `docs/build-guide.md` -- the deployment guide for end users and professional services, exported
  from a Claude Doc. Its code blocks are the scripts verbatim: update them whenever a script changes.
- `dist/` is generated and gitignored.

## Commands

```sh
python build/build.py
docker compose -f tests/docker-compose.yml run --rm compile
docker compose -f tests/docker-compose.yml run --rm tests      # grep FAILED in its output
sh tests/live.sh                                               # about a minute; tears down after
python ../logicmonitor-modules-skill/skill/scripts/lm_lint_module.py dist
python ../logicmonitor-modules-skill/skill/scripts/lm_dashboards.py check dist/dashboards/*.json --modules modules
```

## Rules that bite

- Every datapoint is printed through `galeraEmit(port, '<Name>', value)` with the name as a string
  literal: the build reads the names off those calls to check them against the definition. A null
  value prints nothing (No Data); never print a 0 that means "unknown".
- The wildvalue is the port number. Never change that scheme: it would orphan every instance.
- `jdbc.mysql.user` / `jdbc.mysql.pass` are LogicMonitor's own MySQL property names, kept for
  compatibility with its MySQL package (the skill's lint allows them).
- The PropertySource must stay silent (exit 0, no output) on every failure path.
- Every value reaching the harness's `hostProps` goes through a get/set-only stand-in, as on a
  Collector (`ParamMap`, not a `Map`).
- MariaDB 11.4 loads the Galera provider as a plugin and refuses `wsrep_provider_options`
  (`gmcast.isolate` is gone), so the live test partitions a node with `docker network
  disconnect`. Test accounts come from `--init-file` on the bootstrap node and data directories
  are tmpfs, so a node reported healthy is usable and every run starts clean.
- Module counts in this file and README.md are checked by the build.
